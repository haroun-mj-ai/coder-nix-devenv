# coder-nix-devenv

Reproducible dev environment for our Coder workspaces: the same toolchain, at the
same versions, for everyone. No "works on my machine".

There are two ways to get it:

- **Nix-free bootstrap (primary).** Pinned upstream releases, each verified by
  sha256, plus apt for the distro-packaged bits. Needs only Ubuntu, bash and
  curl. See [docs/NIX-FREE-BOOTSTRAP.md](docs/NIX-FREE-BOOTSTRAP.md) for the
  design and the template migration plan.
- **Nix flake (optional / legacy).** The original `nix develop` setup, unchanged
  and still working. See [Nix flake](#nix-flake-optional--legacy) below.

## Quick start (nix-free)

On Ubuntu 26.04 (x86_64 or arm64):

```bash
git clone https://github.com/haroun-mj-ai/coder-nix-devenv.git
cd coder-nix-devenv
./bootstrap/install.sh --dry-run      # see every download, apt step and link first
./bootstrap/install.sh                # base + extras into ~/.local
. ~/.local/share/nixfree-bootstrap/env.sh
./bootstrap/install.sh --verify-only  # every tool vs. the pinned version
```

Useful flags: `--only <tool>` (repeatable), `--prefix DIR` (default `~/.local`),
`--layer base,extras,runtime|all`, and `--write-env` (adds one `source` line to
`~/.bashrc`; without it, rc files are never touched). Run it as your normal user.
apt steps use sudo, and running as root needs `--allow-root`. Re-running is
cheap and safe.

Two things to know during the transition:

- If you still have Nix, `~/.nix-profile/bin` is probably ahead of `~/.local/bin`
  on your PATH, so the Nix copies win until you reorder it. `verify.sh` ignores
  Nix on purpose.
- **Never `rm -rf /nix` on a live workspace.** herdr, code-server, the shared
  browser and several daemons execute from `/nix/store` today. See
  [the decommission order](docs/NIX-FREE-BOOTSTRAP.md#what-breaks-without-nix-and-why-you-must-never-rm--rf-nix-on-a-live-box).

### What's included

[docs/TOOL-SOURCES.md](docs/TOOL-SOURCES.md) lists every tool with its Nix
version, upstream version, exact source URL, license, and any version delta. It
is generated from [`bootstrap/manifest.tsv`](bootstrap/manifest.tsv), which also
holds the sha256 of every artifact. [docs/DEAD-URLS.md](docs/DEAD-URLS.md) is
the URL audit.

### Bumping or adding a tool

1. Edit the tool's row in `bootstrap/manifest.tsv` (version and both arch URLs).
2. Fetch and hash the new artifacts. Never paste a hash from a web page:
   ```bash
   ./bootstrap/update-hashes.sh --only <tool>
   ```
3. Regenerate the table, install, verify, and commit:
   ```bash
   ./scripts/render-tool-sources.py
   ./bootstrap/install.sh --only <tool> && ./bootstrap/verify.sh --only <tool>
   git commit -am "Bump <tool> to <version>"
   ```

`nodejs_22` is pinned deliberately to match the frontend's production
Dockerfile. Don't bump it until production moves.

## Nix flake (optional / legacy)

You need Nix with flakes enabled.

```bash
git clone https://github.com/haroun-mj-ai/coder-nix-devenv.git
cd coder-nix-devenv
nix develop
```

That drops you into a shell with the full toolchain on `PATH`. Nothing is
installed globally, and nothing is left behind when you exit.

To install the toolchain into your user profile permanently instead:

```bash
nix profile add github:haroun-mj-ai/coder-nix-devenv
```

To grab a single tool without installing anything:

```bash
nix shell github:haroun-mj-ai/coder-nix-devenv#terraform -c terraform version
```

### Adding a package

1. Find the attribute name on [search.nixos.org](https://search.nixos.org/packages).
2. Add it to `toolchainAttrs` in `flake.nix`, under the right category — that
   attrset is the only place the toolchain is declared.
3. Refresh the table and commit:

```bash
./scripts/export-packages.sh   # paste output into the table above
nix develop                    # confirm it resolves
git commit -am "add <package>"
```

Unfree packages need nothing special — `allowUnfree` is already set inside the
flake, and the generated table will label the new package's license for you.

### Unfree packages — read this before you fight it

Two packages here are unfree: **terraform** (BUSL 1.1) and **ngrok**. This flake
sets `config.allowUnfree = true` internally, so `nix develop` and
`nix shell ...#terraform` on *this repo* just work.

Outside this repo, unfree is where most people lose an afternoon, because Nix
reads its config from three different places depending on how you invoke it:

| How you invoke Nix | What enables unfree |
| --- | --- |
| This flake (`nix develop`, `nix shell <repo>#pkg`) | Already handled — nothing to do |
| Channel-based (`nix-shell`, `nix-build`, `<nixpkgs>`) | `{ allowUnfree = true; }` in `~/.config/nixpkgs/config.nix` |
| Plain flake (`nix shell nixpkgs#pkg`) | `NIXPKGS_ALLOW_UNFREE=1` **and** `--impure` |

That third row is the trap. Flake evaluation is *pure*, so it cannot read
`~/.config/nixpkgs/config.nix` **or** your environment variables. This fails
even with the variable exported:

```bash
export NIXPKGS_ALLOW_UNFREE=1
nix shell nixpkgs#terraform     # error: refusing to evaluate ... unfree license
nix shell --impure nixpkgs#terraform   # works
```

To avoid typing `--impure` forever, register this repo as a flake named
`unfree` and use it as your everyday nixpkgs:

```bash
nix registry add unfree github:haroun-mj-ai/coder-nix-devenv
nix profile add unfree#slack    # no --impure, no env var
```

Free packages resolve through `unfree#` too, so you can use it for everything
and stop thinking about licenses.

#### Debugging tip

The unfree assertion fires when the derivation's `outPath` is forced, not when
its metadata is read. So this is a **false pass** — it succeeds even when unfree
is blocked:

```bash
nix eval nixpkgs#terraform.name        # "terraform-1.15.8"  <- proves nothing
nix eval nixpkgs#terraform.outPath     # this is the real test
```

### Notes for maintainers

- `nix profile install` is a deprecated alias for `nix profile add` as of Nix
  2.35. Both work; new docs should say `add`.
- `nix profile list` prints a multi-line block per package. Do not pipe it
  through `head` to skim it — you will cut off the inventory partway and think
  the profile is smaller than it is.
- The Coder `NIX` template consumes this flake, pinned by SHA in its
  Dockerfile's `DEVENV_REV` build arg. Changing the toolchain therefore takes
  two steps: merge here, then bump `DEVENV_REV` in the template and
  `coder templates push`. The pin is deliberate — tracking `main` would make
  the image build non-reproducible, yielding different toolchains depending on
  when it ran.
- A running workspace is *not* a reliable picture of the toolchain. Its profile
  accumulates hand-installed extras and can lag the pinned revision, which is
  why `scripts/export-packages.sh` reads the flake rather than
  `nix profile list`.
- The template's image build re-verifies every tool in this flake, plus asserts
  that `docker` still resolves to `/usr/bin/docker`. If you add a package here
  that shadows something the image installs via apt, that build fails on
  purpose.
